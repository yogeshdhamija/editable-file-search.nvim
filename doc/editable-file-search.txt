*editable-file-search.txt*

Author: Yogesh Dhamija <yogeshdhamija@outlook.com>

This plugin provides |:FILESEARCH|, which turns the current window into a
fuzzy search of the files under the current directory -- as a plain, editable
buffer. Type a query and the results update as you go, as in fzf; then whittle
them down with ordinary editing, the way you would any other text.

Requires Neovim and ripgrep (`rg`).

Its commands are all capitals, so that they can be abbreviated: see
|user-cmd-ambiguous|.

						*:FILESEARCH*
:FILESEARCH [query]	Search the files under the current directory, in this
			window, starting in Insert mode on the query. [query]
			prefills it. Each time is a new search, in a buffer of
			its own; see |editable-file-search-buffers|.

					*editable-file-search.open()*
require('editable-file-search').open([{query}])
			The same, from Lua. Pass a query from a script, a
			Visual selection say, this way rather than through
			|:FILESEARCH|: the command line would take a `|` or
			`"` in it as the end of the command. A query of
			several lines is joined into one, with spaces.

The buffer looks like this: >

	Query: init nvim
	Command: rg --files --no-messages --hidden --glob=!.git/
	Results: 2 matches among 4,210 files in ~/Stuff   <CR> opens · ...
	──────────────────────────────────────────────────────────────────
	.config/nvim/init.vim
	.vim/plugged/nvim-nio/tests/init.vim
<
Line 1 is the query. Every line below it is a result: a path relative to the
directory searched. Both are ordinary text, so anything that edits text works
on them, yanking and pasting included. "Query:", the "Command:" and
"Results:" lines and the rule under them are not text -- they are drawn by the
plugin (|extmarks|) -- so they cannot be edited, deleted or yanked, or
mistaken for a path. The "Command:" line shows the command that listed the
files, flags and all; see |:CHANGEFLAGS| to change them.

The files are listed in the background, so a big directory doesn't hold up
the editor. Until the list is in, the "Results:" line says "Loading…", and
the query can be typed meanwhile. The results are then written all at once,
for the query as it is by then: never part of them at a time.

Changing line 1 runs the query over every file again and redraws the results.
A path matches if the query's characters appear in it in order; a query of
several words keeps only results matching all of them, in any order. Case is
ignored. The best matches come first: each matched character counts for more
at the start of the path or right after a `/`, at the start of a word, or
right after the character matched before it -- and most for that, so that
`lib` puts `lib/x.so` before `lua/images/back.png`. Where a word could match
in more than one place, it's taken as matching the last, so the file name
wins over a directory of the same name. Equal matches go shorter path first,
then in the order of the file list, which is sorted. The characters each
visible result matched on are highlighted, and its directory dimmed, so that
the file name stands out (see |editable-file-search-highlights|).

The results are written a page of 1,000 at a time, so that a query matching
most of a very large tree doesn't fill the buffer with all of it. When there
are more, the "Results:" line says "first 1,000 of" how many; |:MORE| adds
the next page.

Nothing but line 1 is ever redrawn, so the results can be narrowed by hand
and stay that way: `dd`, `d}`, `:g/test/d`, `:v/lua/d`, |:NARROW|. These act on
the results in the buffer, so on the pages shown. Once the results are
anything other than exactly the first pages of what the query gives, the
query is marked "Query (Note: NARROWED):" and the "Results:" line says how
many are left. Editing the query starts over from every file again.

`u` undoes as usual, a step at a time: a query together with its results, or
one narrowing. Undo puts back the results as they were at that point, rather
than searching afresh, so undoing an edit to the query brings back any
narrowing that edit threw away. `CTRL-R` redoes.

						*:NARROW*
:NARROW {text}		Keep only the results that fuzzy-match {text}, in
			the order they were in. Only in a |:FILESEARCH|
			buffer. Repeat it to narrow further; `u` undoes one
			at a time. Like any other narrowing, it acts on the
			results in the buffer: the pages shown, not the
			pages after them.

							*:MORE*
:[count]MORE		Add [count] more pages of results, or one, at the
:MORE [count]		end. Only in a |:FILESEARCH| buffer. They are the
			pages after the last one with any result still
			showing, so results taken out of a page stay out.
			`u` takes them back.

						*:CHANGEFLAGS*
:CHANGEFLAGS		List the files again, with the flags made by answers
			to a prompt for each flag in
			|g:editable_file_search_flag_prompts|. Only in a
			|:FILESEARCH| buffer. Answer `y` to have the flag,
			`n` not to, or <Enter> to leave it as it is; <Esc>
			cancels. Every flag is asked about, always in the
			same order, so the answers can be typed ahead from
			memory: `yyny`. Flags that aren't asked about are
			left as they are.

:CHANGEFLAGS {flags}	List the files again with {flags} added, skipping any
			already there.

:CHANGEFLAGS! [flags]	List the files again with [flags] as the only flags;
			with none, there are none.

{flags} are split into words at spaces; type a space in a word as `\ `. A
flag is a word starting with `-` and the words after it that don't, which are
its values: `-g !.git/` is one flag. The flags are there only if their words
are, together and in order, as whole words: `--no-ignore-vcs` doesn't count as
`--no-ignore`. They are compared as written, too, so `-.` isn't taken for
`--hidden`, though rg treats them the same.

It is still the same search, in the same buffer, so the |jumplist|, marks and
the alternate file all still lead to it, and the query is kept. But it starts
over as a new search does: the results go at once, "Loading…" until the new
list is in, and then come for the query as it is by then, narrowing gone.
Undo starts over too, from when the results go: `u` can't take back a change
of flags, nor anything before it. Run :CHANGEFLAGS again to change them back.
With the flags as they were, it lists the files again all the same, so new
ones show up.

If the command fails -- given a flag rg doesn't know, say -- the error is
shown and the search goes back to the flags and files it had, with the
results redrawn for the query.

<CR> opens the file on the cursor line in this window. On the query line,
from Normal or Insert mode, it opens the top result. Paths are relative to
the directory searched, not the current directory, so they still open after
a |:cd|; |gf| and CTRL-W_f work on them too. A line typed or pasted in as an
absolute path opens as it is.

Opening a result is a jump, so CTRL-O comes back to the search with the
cursor where it was and the results as they were. The search buffer is
listed, so it shows in |:ls| and can be reached with |:buffer| as well.

					*editable-file-search-buffers*
Each search is a buffer of its own, named `filesearch://` followed by a
number and the directory searched: `filesearch://1/home/me/project`, then
`filesearch://2/home/me/project` for the next search there, and so on. Every
|:FILESEARCH| starts a new one, with the file list fetched afresh, so new
files show up. Earlier searches are left as they were, narrowing and all, so
several can be open at once, side by side or one after another in the same
window. They stay listed until |:bdelete|d.

The buffer is 'buftype' nofile and 'bufhidden' hide: there is nothing to
save, and it is kept rather than wiped when hidden, because a wiped buffer has
its |jumplist| entries dropped along with it. The name is also what lets it
survive |:mksession|: entering a search buffer restored from a session sets it
up as a fresh search of that directory, with the default flags.

Line 1 is always the query: it can be emptied, but not deleted. Deleting it
with an operator -- `dd`, `dj`, `dG`, `Vd` -- leaves it empty, as `cc` would,
and so searches every file again. Deleting it with an Ex command -- `:g`, `:v`,
`:d` -- leaves it as it was, since those are for narrowing the results:
`:v/lua/d` catches the query whenever it doesn't say "lua" itself. Anything
deleted along with it stays deleted. `u` puts it all back.

A new search starts from the empty query and every file: `u` takes back a
query typed, or given to |:FILESEARCH|, while the files were being listed, as
it would one typed after.

The search runs inside Neovim, on every key typed into the query. That is
instant for a project; on a very large tree (a home directory, say, with
hundreds of thousands of files) each key takes up to a tenth of a second or
so, less as the query gets longer. Listing a tree that large can take a
while, but only the search waits for it. A listing past 256 MB of paths -- a
couple of million files -- is stopped, as more than a search can take, and
counts as the command failing: the error is shown, and a new search has no
files, while |:CHANGEFLAGS| goes back to the ones it had. Following symlinks
(--follow) out of the directory is the usual way to get there.

					*g:editable_file_search_command*
The command that lists the files, before any flags: a list of words, or a
string, split into words at whitespace. It is run in the directory searched,
without a shell, and should print one path per line, relative to it.
|:CHANGEFLAGS| never changes it. The default: >
	let g:editable_file_search_command =
		\ ['rg', '--files', '--no-messages']
<
					*g:editable_file_search_flag_prompts*
The flags |:CHANGEFLAGS| asks about, in this order, and whether a new search
has each: a list of dictionaries, each with a "flag", given the way the
command is, and a "default", |v:true| or 1 for a new search to have the flag.
The default lists hidden files and leaves out the inside of .git directories.
It doesn't follow symlinks: one out of the directory can lead anywhere
(Wine's `z:` leads to /), and the listing then never ends: >
	let g:editable_file_search_flag_prompts = [
		\ {'flag': '--hidden',      'default': v:true},
		\ {'flag': '--glob=!.git/', 'default': v:true},
		\ {'flag': '--no-ignore',   'default': v:false},
		\ {'flag': '--follow',      'default': v:false},
		\ ]
<
These are rg's flags, so for another command, set both. For git's tracked
files, with untracked ones a `y` away: >
	let g:editable_file_search_command = 'git ls-files'
	let g:editable_file_search_flag_prompts = [
		\ {'flag': '--cached',                   'default': v:true},
		\ {'flag': '--others --exclude-standard', 'default': v:false},
		\ ]
<
					*editable-file-search-highlights*
The colors come from these groups, each linked by default to the one shown
(see |highlight-groups| and |group-name|):

	FileSearchLabel		"Query:", "Command:",	Identifier
				"Results:"
	FileSearchText		the command and counts	Normal
				after them
	FileSearchNarrowed	"(Note: NARROWED)"	WarningMsg
	FileSearchSummary	the hints after those	Comment
	FileSearchSeparator	the rule under them	Comment
	FileSearchDirectory	each result's directory	Comment
	FileSearchMatch		matched characters	Special

To leave directories undimmed, say: >
	highlight link FileSearchDirectory NONE
<
